# Dream 的产品路线图

这是一份讨论稿。下列里程碑按依赖排序，进入下一阶段取决于使用效果。

## 想做成什么

让新会话具备一个老项目成员最有用的能力：知道这里做过哪些决定、哪些地方有例外，以及遇到类似问题时，上次怎样验证了结果。用户可以追问依据，可以改掉一条经验，也可以撤回一次整理。

用同一个发布任务贯穿验收。项目以前用旧脚本；后来生产环境改用 `make release`，staging 仍用旧流程。再后来，团队发现某项检查只在正式发布时需要。新会话应能给对当前环境的步骤，说明决定何时改变，并在用户临时要求改变这一次的做法后，下次仍能恢复项目默认。这是拟议的产品验收场景。

## 第一阶段：可靠地完成一项任务

连续运行的一批任务共用一个宿主子代理，每次交接都附完整固定规则。插件决定何时切换任务。来源交付、草稿验证和检查点保存都成功后才发下一项；部分提交和可修正的失败留在当前任务。重复提交返回已经确认的结果。中断后以最后一项成功保存的工作为准。

验收覆盖三种故障：A 未完成时请求 B，A 提交后丢失工具回执，A 保存后宿主退出。分别核对交给模型的任务、待审文件和恢复后的第一项。记录每项任务的缓存读取、输入输出和耗时，结束条件由任务状态决定。

## 第二阶段：记住一条决定怎样演变

优先支持三个日常问题：“现在怎么做”“上次为什么改”“这个环境是否例外”。利用现有 Markdown、History、逐条引用和项目范围，把当前决定、适用条件、替代关系及出处连起来。用户只说过“改成 X”时，原因保持未知。用户明确说“仅这一次”时，这次执行和长期默认分别处理。

首个可用版本只覆盖用户明确纠正过的决定。用同一项目的一条生产规则和一条 staging 例外测试当前答案、历史答案、一次性覆盖和撤回。两种环境分别提问，可以直接发现“生产修好了、staging 被改坏了”。

## 第三阶段：从实际工作里学到项目经验

Dream 可以把几次会话里分散的材料整理成一条待审经验，写清遇到的现象、适用条件、尝试过的动作、观察到的结果及原始出处。首次接入优先选终端验证结果，引用宿主会话中的命令、可确认的退出状态和必要结果摘录。助手自己说“修好了”仍保留为助手陈述。跨会话综合单独引用各次观察，保留反例，让用户决定是否采纳归纳。

验收使用成对的新任务。一题条件相同但换一种说法，检查是否能少走一次弯路；另一题只改变一个关键条件，检查是否还会误用经验。两题都跑普通召回与 Dream 整理两个版本，记录任务是否完成、做了哪些无效尝试、用户需要纠正几次。

## 第四阶段：用项目自己的历史检验下一版记忆

让用户选少量过去纠正过助手的问题，一次整理产生候选记忆后，后台用两个隔离快照分别回放。审阅时可看到“哪些回答变好了、哪些原本正确的回答变差了、哪些仍缺证据”，再决定是否应用。先做成开发者可运行的实验；只有回放能稳定找出真回退，再接入日常审阅。

题目和预期行为需在生成候选草稿之前冻结。有测试答案的后续对话和评分标签只对评测器可见。模拟回答、失败样本和评语留在隔离环境，以免下一轮 Dream 把它们当作项目事实。

## 用什么决定是否继续

- 共用基线取同一份已有笔记和相同历史，B 直接召回，C 运行 Dream 并按正常规则应用。用同一模型在新会话里答题，逐题列出由错变对和由对变错。单列待人工确认、未应用和每轮成本。
- 公开题先用 [LongMemEval-S](https://github.com/xiaowu0162/LongMemEval) 检查知识更新、跨会话推理和信息不足。项目回归题检查中文条件、一次性要求、撤销和真实动作。流程经验阶段参考 [LongMemEval-V2](https://github.com/xiaowu0162/LongMemEval-V2) 的工作流与环境例外题型。
- 优先解释回退发生在哪一步：收集时漏了例外、整理时改错、召回时选错，还是模型看到了正确记忆仍做错。根据定位修改对应环节。
