## 3. 四个基准现象

### 3.1 十一条旧笔记

11 个主题文件全部存在且自称现行，但验证台账只有更晚写入的条目覆盖。数量本身不是问题；问题是下面的查找入口。

### 3.2 首轮索引为空

同一次注入的 `<index>` 与 `<hot-set>`：

```text
<index>
(no verified current notes; use memory_search or memory_read for the catalog)
</index>
<hot-set>no note has an explicit current status plus verification yet; 11 topic(s) remain available via memory_search or memory_read.</hot-set>
```

新会话只看得到「去搜索」，看不到任何笔记名称；`STATUS: current` 没有台账时不算可信，而台账目前只在 Dream 及更正路径写入（`src/dream.js:1263`、`src/write-review.js:150`），日常 `memory_save`/`memory_update` 不写。

### 3.3 失败预览仍算待处理

`src/status.js:1102-1122` 只隐藏 `manifest.coverageComplete === false` 的 v2 预览：清空 `lastPlanPath` 并写 `lastError`。仍然存在的问题：

- 一个方案若每一项都被证据门禁拒绝，`lastPlanPath` 依旧保留，页面继续显示为可审核方案（待处理）。
- `pendingProposal` 缺失文件或超期时才由 `readiness.js:230-241` 报 `pending-proposal`，正常存在即计入门禁。

本样例中 `.state.json` 的 `pendingProposal` 为空，失败的是整理阶段（见 3.4），没有留下可应用的预览；这两个分支要在阶段 5 的待处理统计里一起处理。

## 4. 附：HTTP 项目定位（阶段 0 修复）

基线行为：请求显式带 `sessionId`，但当前进程解析不到该会话时，`resolveProject` 会回落到「唯一已加载的项目」。页面过期或会话被关闭后，读写仍会落进当前项目。

已改为：显式会话解析失败直接返回 `400 unknown-session`（`src/http.js`），无会话时才允许使用唯一项目；回归测试 `test/http-project-routing.test.mjs`（过期会话读/写均 400 且不落盘、有效会话读写成功、无会话仍可用）。测试夹具 `httpEnv` 现在注册一个 `s1` 活会话，因为真实页面总会带会话 id。
