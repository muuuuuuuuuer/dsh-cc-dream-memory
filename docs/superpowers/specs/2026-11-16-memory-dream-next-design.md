# 记忆与 Dream 下一阶段设计

2026-11-16。设计建议，供评审和后续实施。基于本地 0.20.0、HEAD `4c0acd3` 及当前 `src/dream-agent.js` 未提交的读取提示改进。当前工作区另有 CHANGELOG 修改和 `test/dream-read-hint.test.mjs`。

**设计目标**

让一次工作中得到的经验，在以后遇到合适的问题时能够被找到、正确使用，并随着新证据而修正。普通记忆负责及时记录与使用，Dream 负责跨会话整理、纠错和综合。Wiki 可以读取同一批记忆，作为独立的组织与浏览功能发展。

这份方案选择继续使用本地 Markdown、现有 MemoryStore 和单个 Dream agent。新增结构围绕三个问题展开，分别是内容如何表达、如何找到、整理怎样续作。各阶段完成后都有独立可用的功能。

当前 agent 仍最多运行 14 轮，默认候选选择代码回退到 8 个会话，每轮优先比较旧页，取消和超时会清除工作副本。`dream-run.js` 中仍存在旧格式工作单元帮助函数，复用前应检查生产调用方，恢复能力以 `DreamAgent` 的实际调用链为准。

本轮根据源码确认上述实现状态。之前的测试结果属于之前的代码快照，实施时重新运行对应回归与仓库校验。

**二、日常使用应是什么样**

用户完成一次排障，普通记忆保存“观察到的现象、采取的动作、结果和条件”。下次遇到相似问题时，召回先判断条件是否适合，再提供经验和来源入口。

数次相关经历积累后，Dream 将它们放到一起，补充例外、收窄适用条件、合并重复内容，或者提出一条新的经验总结。用户在现有 Memory 页面查看差异并处理。后台中断时，下一次从已保存的工作单元继续。

示例内容如下，示例中的技术结论是假设数据。

```text
标题  Windows 环境中的重复重试问题
内容类型  experience
结论依据  observed
适用条件  Windows，客户端与上层封装同时开启重试
观察  一次请求失败后出现多次重复调用
动作  关闭上层封装的重试
结果  同一复现场景中的重复调用消失
解释  两层重试叠加可能是原因，尚待其他场景确认
来源  某会话的用户描述和执行结果
```

只有一次观察时，正文保留“一次复现场景”的范围。新增相反案例时，Dream 可以补充例外或修改解释。修改文件的时间只描述文件维护时间。

**三、记忆的数据表达**

沿用现有 `user / feedback / project / reference` 四种 type。新增以下可选标量 frontmatter，由现有轻量解析器直接支持。

| 字段 | 值与用途 |
|---|---|
| id | 首次通过新写入路径保存时生成的稳定标识，重命名沿用 |
| kind | fact、experience、synthesis、navigation，缺省为 fact |
| evidence | stated、observed、inferred、unknown，缺省为 unknown |
| applies_when | 页级适用条件，自然语言字符串，缺省表示未记录条件 |
| valid_from / valid_until | 已知的生效时间与失效时间，缺省表示未知 |

`evidence` 表达正文主结论的依据。stated 要保留说话者，用户陈述、助手陈述和工具输出通过来源记录区分。inferred 总结可以建立在 observed 材料上，阅读确认只表示用户接受该版本。引用核对、用户接受、结论依据是三个独立信息。

现有 basis 表达写入归因，confidence 供写入策略使用，新增 evidence 表达内容依据。自动抽取仍通过 inference/low 进入已有写入策略；只有携带可核对的原始观察来源时才能将 evidence 标为 observed。单纯的助手成功声明保留为 stated 并标注助手身份。旧页依据缺失时采用 unknown。

STATUS 与 History 继续使用 `memory-body.js` 的现有表达。生产路径统一通过该模块计算当前内容，避免出现两套状态。正文中包含多个条件时保留分节，同一页的元数据应概括共同条件；条件和依据明显不同的主题由 Dream 拆页。缺少条件的旧页保持可检索，读取结果明确标注条件未记录。

经验正文建议包含观察、动作、结果、解释与例外。模型只填写有材料支持的部分。原有 `Applies when:` 内容继续可读，首次正常编辑时可提取为页级字段；字段与正文冲突时提示待整理并展示两者。

来源随正文持久保存，包含 session id、seq、原文摘录、来源角色。Dream 提案中另外保留源事件指纹、页面版本与摘录核对结果。当前的运行记录用于精确审阅，已接受页面保留足够的来源入口供未来查证。来源不可访问时显示 unavailable，已有内容继续可读。

同项目页面关系先使用普通 Markdown 链接，表达“补充、替代、例外、综合依据”。稳定 id 用于内部重命名识别。合并时更新入链和旧文件别名，普通链接打开、模型读取及索引都经同一解析入口。跨项目关系需要显式指定项目身份和读取权限。

新增字段必须贯穿 frontmatter 序列化、store 写入、普通工具、Dream 工具、元数据目录、HTTP 编辑、导入导出和 shadow/undo。现有 FRONTMATTER_FIELDS 是显式白名单，只修改解析器会丢失字段。

所有编辑入口采用相同字段规则，省略可选字段保留旧值，显式 null 清除可选值，空字符串按字段校验转换为缺省。id 由宿主生成并维护。旧客户端仅提交正文时，其余新字段完整保留。文件全量导入则以导入内容为准，并在替换预览中展示被清除的字段。

明确两种版本用途。rawHash 继续绑定 exact bytes、写入并发与审阅；contentVersion 由规范化后的 name、description、type、kind、evidence、applies_when、有效时间和完整正文计算。STATUS 属于正文，因此参与版本。modified 等维护时间不进入 contentVersion。条件与依据变化触发召回去重更新、目录失效和依赖重查。现有 entryVersion 扩展为该契约，各调用方一次性接入，缓存版本升级后重建。

**四、普通记忆如何写入和纠正**

同步调整 `inject.js`、`auto-extract.js` 和 Dream 指令中的保留标准。可从代码直接读取的状态继续通过代码查询。经过实际工作得到的观察、失败尝试、用户确认和适用条件可以保存为经验。

自动抽取保留其低置信度写入规则。主会话明确要求记住的内容使用现有保存入口。模型推断必须保留推断措辞，工具写入校验来源角色与字段合法性。

为已有 `memory_update` 增加可选的精确段落替换模式，参数为 file、expectedHash、oldText、newText。oldText 必须唯一匹配，成功后返回新版本。正文整体替换继续支持。自动抽取收到 TOO_LONG 后使用分段写入或主动压缩并重试，未完成的写入保持游标。

一次完整读到的事件可以继续沿用现有抽取进度。跨事件推断引用多个来源。用户修正一条经验时，通过普通纠正路径立刻生效，并为 Dream 生成相关主题待办。

**五、召回与索引的下一步**

沿用当前两步召回，先生成相关候选，再由模型选择。新增信息进入同一条路径。

1. 后台维护可重建目录，记录名称、描述、kind、条件、状态、有效时间、正文主题词、页面关系及文件指纹。
2. 文件写入、外部修改、恢复备份会使对应目录项失效。由写入钩子和后台文件检查更新，查询时优先使用已校验目录；未索引页面保留元数据候选资格。
3. 候选预排先排除明确 retired 或已失效的内容，再综合问题相关性与条件。中文词组和同义称呼由正文主题词与 Dream 描述维护支持。
4. 模型选择时看到简短条件和依据标签。条件不明时给出条件提醒，已明确不符合的经验退出默认候选。
5. 展示正文时按完整语义段落组织，条件、例外和结论一起送入上下文。长度不足时提供短摘要与原文读取入口。
6. 同会话去重记录 file/id 与版本。原页面被纠正后可以再次显示更新摘要，重复的相同版本只展示一次。

MEMORY.md 继续承担启动索引。Dream 可以改进描述、建议顺序和创建小型主题导航。目录改动应形成显式 index 提案并具有基准 hash，支持单独预览、接受和撤销。当前只有页面写入工具，索引通常伴随页面更新，独立维护能力需要增加。

第一阶段采用本地关键词目录，利用已有 tokenizer。候选覆盖后续确实受到同义表达限制时，再评估向量索引。目录索引损坏可从 Markdown 重建，普通读取照常可用。

阶段 A 的目录只提取现有正文、描述和条件中的词语，Dream 已有描述改写可补充同义称呼。导航页面关系的自动维护、独立索引提案属于阶段 C。第一阶段的用户收益以有明确词语或同义描述支持的召回为验收边界。

**六、Dream 的工作单元与恢复**

保留单 agent 工具循环，将长期运行拆为可以保存的工作单元。单元通常是一段会话的新内容及关联页面，或者一个待解决的主题矛盾。模型可决定搜索和整理顺序，宿主负责记录来源范围、读写版本和完成状态。

工作来源包括新会话片段、被纠正的记忆、未完成单元，以及变化页面的相关主题。调度优先处理显式纠正和续作，每批同时给最老的未处理工作留一个机会。启动时读取元数据和当前单元，相关旧页按需要读取。

```text
排队 → 运行 → 待审 → 已结算
         ↓       ↓
       可继续   保留待定提案
         ↓
       恢复运行
```

每个 run 使用 `.dreams/<runId>/shadow/` 保存工作副本，manifest 记录其位置。恢复复用相同 runId；新运行使用新的目录。旧 `.dreams/shadow` pending 在首次操作时按原位置读取，结算后由新运行使用新布局。

阶段 B 维持每个项目一个活动 run。待审时该 run 可以继续分析与待审组无依赖的工作；新产生的组以新 proposalId 追加，已显示组的版本冻结。存在读写重叠时等待对应组结算，再以当前 live 版本重新规划该单元。用户开始另一个 focus 时将其排入当前 run 的后续工作。所有组处理完成后归档 run，再创建下一 run。

每个未结算组独占其目标页与索引改动范围；其他单元使用 live 加自身改动的视图，不能默默读入另一待定组的输出。确实需要依赖时建立显式依赖并等待前置组结算。审阅请求携带 runId、proposalId 和 proposalRevision，组内修改生成新 revision，旧请求返回 stale。当前旧接口只在一个可明确对应的整批待审结果上兼容，出现多组时要求刷新到新接口。

manifest 扩展 schemaVersion、checkpointVersion、工作单元、源事件覆盖、读取页面版本、生成页面版本、提案依赖和下次工作摘要。摘要只保存工作计划与外部可核对的结果。

工具写入完成后，先持久化对应工作产物和来源记录，再通过原子 manifest 更新发布检查点。检查点引用的内容以版本快照保存在 run 目录，manifest 发布失败时，上一个检查点仍可读取。恢复时忽略未被检查点引用的孤立产物。

会话范围使用 session id、seq、字符区间及内容指纹。若同一事件修改，相关单元失效并重读；只追加新事件时，为新范围排队。旧页变化时，只重做依赖它的未结算提案。页面冲突经现有版本检查返回到审阅界面。

运行触及内部轮数、provider 上限或超时时，保存检查点并标为 resumable。手动取消后等待用户再次启动，自动任务的资源暂停可在下次调度继续。真正不可恢复的错误显示 failed 并保留最后检查点。面板显示已完成单元、剩余单元、待审提案及暂停原因。

现有配置中的成本策略继续作为真实执行约束。普通用户只需启动、继续、停止和处理提案。

**七、阅读进度、提案和人工决定分别结算**

为每个工作单元记录 analyzedRanges 和 proposalIds。已分析且没有提案的范围可以直接结算；生成提案的范围必须先保证提案及来源持久保存。后续运行可以复用分析产物，待审内容在同一 run 内保持可追踪。

保留 session_done 的阅读覆盖含义，新增 Dream 内部工具 work_done，参数为 unitId、已分析范围、proposalIds、remaining 和简短结果。宿主核对所声明范围已读完整、输出产物已持久化且无未解决写入错误，再发布单元完成检查点。只有这一检查点能将材料标为 analyzed。读完后尚未 work_done 就中断的单元恢复为未完成，复用已持久化来源与草稿。

源范围与提案组是多对多关系。每个已分析范围记录全部关联 proposalIds，全部依赖组有最终决定后才更新旧的 processed/coverage 状态；暂缓组维持待定关联，调度从分析账本中识别已做工作，直接复用产物。跨片段解释仍未完成时，work_done 将相关范围列入 remaining，避免把孤立半段当成完整结论。

提案以依赖组为接受单位。合并页、被删除的原页、依赖该内容的总结和索引更新属于同组，或者有显式的前置依赖。独立组可以分别处理。

| 操作 | 记忆结果 | 后续处理 |
|---|---|---|
| 接受 | 按审阅版本写入，记录事务与来源 | 单元的该组结算 |
| 拒绝 | 保留现有记忆，保存具体差异和来源指纹 | 同源同版本提案去重，新证据允许再次提出 |
| 暂缓 | 提案持久保留 | 不再次请求模型生成同一提案 |
| 丢弃本次草稿 | 删除待定产物，保留必要审计记录 | 对应未采用材料重新进入待办 |
| 撤销接受 | 使用现有备份和版本冲突检查恢复 | 记录撤销事件，该结论待重新检查 |

“暂缓保留提案”是本方案提出的产品变化。当前全局 discard 会清空副本并允许重跑。新 UI 将“以后再看”和“丢弃草稿”分开，旧接口 discard 继续对应丢弃草稿，新增明确的 defer 接口。

引用匹配继续绑定页面版本。审阅页展示“原文已找到”“综合推断”“来源不可用”等信息。人工明确确认继续使用当前 confirm 行为。后端负责精确版本、来源身份和事务一致性，模型与用户判断语义支持程度。

应用事务需要把页面、索引、提案决定与覆盖结算关联到同一 transactionId。复用现有备份及 switch 元数据，以 prepared、files-written、settled 阶段记录恢复状态。崩溃后先完成结算或按备份恢复，再接受新切换。重复 transactionId 返回原结果。撤销同时恢复索引、关系和相关决定记录，受后续修改影响时按现有冲突方式处理。

事务日志逐文件保存 beforeHash、afterHash、备份与目标产物位置。所有目标落盘并核对后原子写入 files-written，此记录是持久提交决定。恢复时，存在该记录且目标均匹配 afterHash 就完成 state 结算；只有 prepared 时，对匹配 beforeHash/afterHash 的文件恢复备份。发现任何第三种 hash 时进入 recovery-conflict，保留外部编辑并暂停该项目的插件写入，界面显示冲突和恢复选项。

普通 save/update、抽取、Dream 应用在同一写入口先检查未完成事务。恢复完成前读取使用上次已结算视图，受影响页从备份读取，其余页从 live 读取，并显示恢复状态。settled 后统一发布新视图。人工直接改文件产生的第三种 hash 通过冲突预览供用户选择保留，恢复器不会自动覆盖。状态结算根据 transactionId 幂等执行。

**八、跨会话综合与反馈更新**

Dream 在一个主题出现相关新材料时，可读取其经验、历史替代关系和最近纠正。输出可以是补充条件、例外、纠错、主题导航，或 synthesis 页面。

综合页面引用多条原始材料，标明主结论属于 inferred，给出适用范围和反例。相同原始事件被多个摘要重复引用时，按来源指纹去重，来源身份贯穿回溯。原始依据被纠正或失效时，通过页面关系把相关综合重新排入检查。

暂时只有单次经历时保留该次观察的范围。需要验证的假设写成候选解释，由未来任务中的观察更新。后台 Dream 的工具权限延续记忆和会话范围，新增验证执行应成为单独授权的任务。

复用运行记录与状态文件存储明确反馈事件，字段包含 eventId、memoryId/file、revision、kind、source、at、resolvedBy。kind 初期只有 correction、reject、undo、explicit-confirmation。API 重试根据 eventId 去重。读取量和召回量继续作为排序与运行统计。

普通纠正立即修改对应页面，后台再更新受影响的综合和导航。显式纠正优先级高于一般维护，避免旧解释在多页间继续传播。

**九、实施顺序与代码边界**

| 阶段 | 可交付功能 | 主要文件 | 完成条件 |
|---|---|---|---|
| A | 经验格式贯穿保存与召回，条件感知，长页小段更新 | frontmatter.js、store.js、memory-body.js、tools.js、inject.js、auto-extract.js、recall.js、HTTP 与 client | 新会话可读取正确条件下的经验；旧页往返无内容损失；纠正后同会话能看到新版本 |
| B | 独立 run 工作目录、检查点、续作、提案分组与持久暂缓 | dream-agent.js、dream-run.js、dream-shadow.js、dream.js、state.js、runtime.js、scheduler.js、readiness.js、HTTP 与 client | 任意检查点中断可恢复；已完成产物复用；部分接受后只处理余下组 |
| C | 跨会话综合、轻量关系、反馈驱动更新、索引提案 | dream-agent.js、dream-evidence.js、store.js、recall.js、metrics.js、state.js、HTTP 与 client | 新证据能更新相关旧总结；来源去重；索引及链接与页面一起接受和撤销 |

阶段 A 可增加 `memory-catalog.js`，集中管理可重建目录，避免将召回索引逻辑散入所有工具。阶段 B 的检查点逻辑集中在 `dream-run.js`，由 `dream-agent.js` 调用。阶段 C 的关系先从 Markdown 提取并纳入目录，随页面版本失效。

全程复用现有项目识别、写锁、hash 冲突处理、引用匹配、备份恢复和工具循环。将目前工作区的读取提示改进纳入基线检查。旧文档中已过时的状态在对应阶段交付时更新。

**十、兼容与故障行为**

旧页缺少新字段时按旧格式读入，只有正常编辑才写入补充字段。无法推断的条件和时间保留未知。手工编辑导致内容变化时，索引项和引用判断按版本失效。首次增加稳定 id 时扫描现有 id，冲突页面分配新 id 并更新受影响关系。

旧运行 manifest 按格式版本加载。具有可验证页面副本的旧 pending 继续提供当前预览和切换；缺少新检查点的历史运行支持查看历史，并可从旧会话进度建立新运行。

关联断链时保留源文件与错误提示，综合结论转为待复核。明确过期内容退出默认召回，但仍能通过历史查询找到。provider 输出截断或上下文超限时记录原因并保留工作进度，通过更小工作单元继续。

**十一、交付验证**

每阶段围绕以下真实入口补充必要回归，完成定向测试后运行 `npm test` 和 `npm run verify`。

| 场景 | 需要观察的行为 |
|---|---|
| 关闭 Dream，A 会话记录，B 会话使用，C 会话纠正 | 普通记忆完整工作 |
| 一条旧经验与当前问题同义但用词不同 | 进入候选并能找到正文及条件 |
| 两条结论在不同条件下成立 | 同时保留，召回呈现匹配条件 |
| 一次观察和一个原因推测 | 依据标签与正文保留区别 |
| 生成提案后崩溃、重启、重复请求接受 | 产物可复用，切换与结算幂等 |
| 三个独立组中接受一个、拒绝一个、暂缓一个 | 三种结果持久保存，已处理材料不重生成 |
| 来源页被改，另一个无关页也被改 | 只重查依赖变化来源的单元 |
| 长页读完后局部修改、写入冲突、模型输出截断 | 精确更新或明确失败，完整正文保留 |
| 撤销包含索引和关系的 Dream | 页面、入口和关联一起恢复 |
| 自动任务中断与用户手动停止 | 前者可按调度续作，后者等待手动继续 |

每阶段再用真实模型走一个小型多会话场景，检查最终写入、下一次实际召回和错误恢复。记录耗时、调用次数和完成/恢复结果，用于调整默认工作量。

**十二、设计选择与参考**

本方案由我选择沿用本地 Markdown、单 agent、可重建关键词目录和人工接受 Dream。阶段 A 增加少量可选字段；阶段 B 改变暂缓语义并保留旧 discard 的行为；阶段 C 引入有来源的综合页面。这些属于待评审的设计决定。
